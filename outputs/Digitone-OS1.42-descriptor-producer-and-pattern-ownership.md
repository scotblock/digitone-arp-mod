# Digitone OS 1.42: descriptor producer and pattern ownership

The delayed-note descriptor is **assembled from incoming USB stream control words**, not generated by the traced Digitone sequencer or held-note builders. Its local assembler is `40003830`; the input buffers are posted to USB endpoint 3 OUT. The content originates on the host side of that transfer. The particular host application and its internal musical context cannot be identified from this firmware alone.

On the traced note path, the descriptor carries no source-pattern reference or root/scale snapshot. **There is no established original Digitone pattern owner to recover from these queued notes.** Choosing the receiving track's current pattern at local enqueue would be a new V1 policy. This resolves the firmware-side provenance question while preserving the limitation on host-side provenance.

Firmware remains unchanged. No USB traffic was captured or generated, and no device was contacted.

## 1. Receive-buffer chain

| Stage | Firmware evidence | Result |
|---|---|---|
| Receive initialization | `400037ea` repeatedly calls `400036f6` | Sixteen receive transfer descriptors are created. |
| Buffer selection | `4000373e..40003766` | Input buffer address is `8000ba00 + 0x58*slot`, with 16 slots. |
| Pending input chain | `4000378e..400037a8` | First/current and tail pointers are stored in `4024b264` and `4024b260`; descriptors link through `+34`. |
| Submit receive transfer | `400037d2..400037de` | Transfer is submitted through `40005f92` with logical channel 3. |
| Physical endpoint mask | Table `4016cfe0`; writer `400060d6` | Channel 3 selects mask `0x00000008`, written to `FC0B01B0`. |
| Read completed input | `400038da..400038fe` | Reader follows `4024b264`, checks transfer status, and obtains the received-buffer pointer from transfer `+30`. |

The peripheral interpretation is supported by the [NXP MCF5441x reference manual](https://www.nxp.com/docs/en/reference-manual/MCF54418RM.pdf), chapter 24, especially pages 24-41 and 24-42: `FC0B01B0` primes endpoints, its low four bits select receive buffers for USB OUT, and `FC0B01B4` flushes endpoints. The firmware's channel-3 mask and corresponding receive-flush mask at `400033ae` identify endpoint 3 OUT. This register-map match supports the transport interpretation; it is not independent proof of the precise installed CPU model.

`40005f92` also initializes transfer `+30` from its buffer address at `40005fc0..40005fc4`. Its read of `FC0B014C` at `40005fb6` records a USB frame index, not an endpoint-list pointer. These details distinguish the incoming buffers from a local event-memory queue.

The existing caller at `4009ca96` uses this stream reader for incoming audio/control. Another caller at `400d9356` passes null descriptor/time outputs and consumes audio only. The former's mode-6 branch uses a separate reader at `400043ea`; the precise user-facing names of these mode values are not assigned here.

## 2. The actual local descriptor producer

`40003830` performs two related operations on the received stream:

- Copies stereo sample data from buffer `+20 + 8*frame_index` at `40003936..4000393e`.
- Reassembles control words from buffer `+04 + 4*frame_index` at `400039d2..400039ea`.

The start condition comes from the received buffer's byte `+01`, shifted right by two at `4000394c..40003954`, and checked against the consumed frame interval. The assembler tracks its in-progress position at `4024b250`. It copies **20 four-byte words**, giving an **80-byte descriptor**, and publishes its pointer at `40003a04` when complete. Destination storage uses four rotating slots at `4024b050 + 0x80*slot`. Descriptor-slot stride is 128 bytes; meaningful assembled content is 80 bytes.

The reader does not construct a `0xec` tag, note pitches, track identifiers, or root/scale values from pattern storage in this path. It copies the incoming control words. The later handler `400efcb8` checks the resulting descriptor tag at `400efd00..400efd08` and interprets note items when flag `0x10` is present.

In the normal audio/update caller, a completed descriptor and time can be deferred in globals `41345e60/41345e5c` at `4009cac8..4009cace`; handling occurs through the call at **`4009cae4`**. Pattern capture at that handler therefore occurs after USB arrival and reassembly, potentially also after this local deferment.

The producer has been identified at two levels: **host-supplied stream content**, and **firmware reassembly at `40003830`**. Identifying a specific host-side code function would require host software or protocol evidence not present in the uploaded firmware.

## 3. Pattern ownership of the queued notes

The note-item layout at descriptor `+10` onward is four bytes per item:

```
note byte | velocity byte | track:4 bits + time offset:12 bits
```

The handler accepts tracks 0..7, ignores higher tracks, and stops on a negative note byte. With flag `0x10`, the low four bits of the flags byte encode the inclusive final item index: up to 16 note items fit within the 80-byte descriptor. The resulting queue record contains link, note, velocity, track and due time, as documented in the preceding report.

Neither the note-item extraction nor the queued-event constructor reads a source pattern pointer, a pattern index, root or scale. Track number alone identifies a target track, not a historical pattern.

The separate descriptor word at `+04` also cannot establish pattern ownership in this image. If it is not -1, `400efdf4..400efdfa` schedules callback `400efc50` through `400013cc`. That callback jumps to **`40095d96`**, whose entire function is **`rts`** (`4e75`). It is a no-op in this OS image, rather than a hidden pattern-selector implementation. This finding does not assign a meaning to that word in other products or protocol versions.

Other descriptor flags control transport-related state through the already traced routines. This report does not claim every byte of the protocol is understood. The narrower, supported conclusion is that **the observed queued-note path has no original-pattern association**, and the input chain supplies external words instead of deriving them from a local generating pattern.

## 4. Consequence for V1

For sequencer and ordinary held-template events, keep the previously established capture points where source pattern/track are explicit. Treat this USB-stream note path separately.

For these host-supplied notes, a possible V1 policy is: **capture the target synth track's receiving-pattern root/scale at local enqueue, and retain those values across later pattern changes until accepted arp replacement**. Capture must happen before linking the delayed node at `400efed6..400efee8`, rather than when the note becomes due. Synth tracks are 0..3; MIDI tracks 4..7 require separate treatment.

This policy is a proposal, not stock behavior or a recovered host snapshot. The known backing layout is `B + 0x3d0*track`, root `+3cb` and signed raw scale `+3ce`. Choosing active backing pointer `41342150` for the receiving context still requires a consistency audit against pattern changes and accepted event ordering. It must not be justified by the canonical-bank expression used in a different held-input route without checking the intended policy.

If V1 must instead reproduce a scale that existed in the host or on the device at some earlier transmission time, that context must be supplied by a protocol extension or another established historical mapping. The traced note item cannot recover it. No such protocol change is proposed or implemented here.

Storage is still unresolved: all five words of each delayed node are occupied. A new snapshot cannot be appended without auditing allocation, copies, reclamation and hard-coded strides. Free-looking upper bits or descriptor-slot padding are not proven storage reservations.

## 5. Checks and limits

`digitone_descriptor_provenance_checks.py` passes seven bounded PC scenarios: all 21 word-aligned two-chunk splits, a descriptor spanning three seven-word chunks, multiple complete descriptors plus a partial tail, note/track/time extraction, 16-item bounds and track rejection, note sentinel/flag handling, and indistinguishable source histories with identical note descriptors.

These are synthetic specification checks. They do not emulate USB, the ColdFire CPU, start detection, interrupts, deferred timing, receive failures or every descriptor command. The example histories demonstrate the missing information in the traced fields; they do not describe an observed host session.

Nine key instruction byte anchors and the channel-3 mask were checked directly against section-3. Results and hashes are saved in `Digitone-descriptor-provenance-check-results.json`. Original SysEx SHA-256 remains `0de87bf55e6bc48bebef5479e0d054f262fb7a0c7f81052dbd195d38569fdfda`; section-3 remains `ba336089d28edc7631df14b12c4a93f8a3c9186a0de8859797a6a3ad05e297f6`.

The remaining task is now concrete: audit receiving-pattern capture timing and a safe snapshot-storage design for this host-input queue, alongside retained context commit/read/reset consistency. Further searching this receive path for a local generating-pattern owner is not supported by the established dataflow.
